# 当前契约、实现原理与验收历史分别维护

一条行为变化应同时保留“要求什么、怎样实现、验证到哪”，避免让历史设计承担当前规格的职责。

## 文档分工

| 位置 | 维护内容 |
| --- | --- |
| `AGENTS.md`、`openspec/config.yaml` | 开发、授权和交付约束 |
| `openspec/specs/` | 已纳入管理的当前行为契约 |
| `openspec/changes/` | 本次行为变更的提案、设计、增量规格与任务 |
| `doc/knowledge/` | 一个主题一篇的实现方法、边界与源码入口 |
| `doc/design.md`、专项协议文档 | 完整架构、调查及版本演进 |
| `doc/tasks.md` | 真正执行的命令、结果、失败和未验证范围 |
| `README.md`、`README.en.md` | 用户可见行为、安装及导航 |

新增能力、协议或行为变化先创建或续用 OpenSpec 变更。实施后核对源码、测试和增量规格，再严格校验、同步与归档。纯说明文档整理可直接完成，不必人为新增行为规格。

## 维护规则

更新一个实现时先搜索关联原子笔记，修改核心结论及入口，并补充分类索引。主题出现两个可独立引用的结论时拆分；历史失败与实测记录留在任务日志中，原子笔记链接它们，不复制大段报告。

旧待办未勾选不自动成为当前任务。格式校验通过、任务框已勾选或归档目录存在，也不能消除真实账号、平台或订阅尚未验证的缺口。

## 源码与验证入口

- [OpenSpec 开发指南](../../openspec.md)与[项目配置](../../../openspec/config.yaml)：当前流程和命令。
- [主规格](../../../openspec/specs/)与[归档变更](../../../openspec/archives/)：契约和决策来源。
- [设计记录](../../design.md)与[验收记录](../../tasks.md)：按日期及最终候选核对。
