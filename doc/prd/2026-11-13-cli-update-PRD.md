**问题描述**：CLI Worker 接入了 17 个 CLI，但插件不显示它们的版本，也没有更新入口。用户只能逐个打开终端，自己判断每个 CLI 是用 npm、Homebrew、官方安装器还是桌面应用装的，再用对应的命令更新。CLI 版本过旧时，模型目录、协议字段或登录流程可能与插件预期不一致，用户很难判断问题出在版本上。现状核对（2026-11-13，main b7949ec）：只有 Grok（`src/host/grok-adapter.ts:235`）和 TRAE CN（`src/host/traecn-executable.ts:14`）在内部执行 `--version`，用于识别可执行文件，结果不展示、也不比较最新版本。插件也没有安装入口：没装过的 CLI 只能照各自官方文档手动安装，再到「高级设置」里填路径。

## 一、背景与问题

1. 安装来源分散。同一个 CLI 可能来自 npm 全局包、Homebrew、官方独立安装器、CLI 自带的更新命令，或由桌面应用（ZCode、WorkBuddy CN、WorkBuddy）托管。用错包管理器会在另一个位置装出第二份，插件实际调用的仍是旧版本。
2. 用户不知道哪些 CLI 过旧。插件设置窗口只显示账号和模型，没有版本信息。
3. 下载经常停滞。国内网络访问 npm registry 和海外安装源时常卡住不动；2026-11-12 升级 DSH 时，就靠「10 秒无增长即中断、再断点续传」才下载完成。更新功能需要内置同样的处理。
4. 参考实现：开源项目 Codingns4DSH（commit 7ccef2a，GPL-3.0）已实现外部 Agent 的安装和更新。其做法是：按可执行文件的真实路径识别安装来源，自动选择对应的更新方式；全局同一时间只执行一个操作；更新期间该 Agent 不接新任务；更新后重新探测，确认版本确实前进。它没有下载停滞续传。本插件是 MIT 许可，**只参考其行为和规则，不复制代码**。调研报告见第十节。
5. 安装同样分散。各 CLI 的官方安装方式（npm 包、官方安装脚本、桌面应用安装包）和前置条件（Node.js、Bun 版本，能否直连官方站点）各不相同。桌面应用默认装在系统盘，Windows 系统盘空间紧张时（实测有机器 C 盘只剩 3.35 GB）需要换位置，换了位置插件又找不到。

## 二、目标用户与使用场景

1. 同时使用多个 CLI 的用户：打开设置就能看到哪些 CLI 有新版本，一键更新，不用记各自的更新命令。
2. 网络不稳定的用户（国内网络、代理）：下载卡住时插件自动续传，不必盯着进度条手动重试。
3. 用桌面应用托管 CLI 的用户（ZCode、WorkBuddy CN、WorkBuddy）：明确告知要到桌面端更新，不误导成可以一键更新。
4. 第一次使用某个 CLI 的用户：在同一页直接安装，装好后插件自动认到路径，下一步去登录。

## 三、目标与成功指标

1. 设置窗口新增「更新 CLI」页，列出全部 17 个 CLI 的当前版本、最新版本和安装来源。
2. 能可靠识别安装来源的 CLI 支持一键更新；更新后重新探测，版本确实前进才算成功。
3. 下载每 10 秒检查一次进度；没有增长就暂停，再从中断处继续，最多 200 次。
4. 识别不出安装来源、由桌面应用托管或包管理器不受支持的 CLI，只给出官方更新方法，不猜命令。
5. 未安装的 CLI 可以在本页安装（2026-11-13 你在设计稿上要求）：纯 CLI 装到官方默认位置；带官方桌面客户端的（ZCode、WorkBuddy CN、WorkBuddy）可以选安装位置，装好后插件自动记住路径。

成功指标：macOS 上可一键更新的 CLI 数。基线 0（插件现在没有更新功能）；目标为第五节 5.3 表中标「自动」的 CLI 全部通过真实更新验收。Windows 单独统计。

## 四、方案概述

- **入口**：设置窗口左侧导航新增「更新 CLI」，位于「智能体设置」之后、「CLI 连接」之前。有可更新的 CLI 时显示数量徽标；更新进行中显示转圈。
- **页面**：页头只有 24px 标题和副标题，不放图标，右侧是「检查更新」按钮。正文按状态分区：可更新、需要手动更新、已是最新（可收起）、未安装（默认收起，每行有「安装」），检查失败时另有「检查失败」分区。
- **安装**：纯 CLI 点「安装」直接装到官方默认位置；桌面应用先在行内选安装位置，再点「开始安装」。下载、续传、取消、互斥规则与更新相同（见 5.11）。
- **更新**：在行内点「更新」后直接开始，行下展开下载进度、实际执行的命令和输出，不另开弹窗。全局同一时间只更新一个 CLI；「全部更新」按顺序逐个执行。
- **后台预加载**（2026-11-13 你要求）：DSH 启动后，等系统空闲时由 Host 在后台低负载地读一遍 CLI 路径、当前版本、最新版本和账号登录状态，存进插件私有缓存。打开页面直接显示缓存，只有缓存里没有或已过期的 CLI 才走加载流程（见 5.13）。
- **Host**：新增 CLI 更新服务，负责版本检查、识别安装来源、执行更新、续传下载、取消和结果核对。Client 只通过 Gateway 调用，不直接执行命令。
- **安全边界**：只由用户在设置页触发，主 Agent 不能调用；命令一律用参数数组执行，不拼接 shell；不读写凭据，不修改 CLI 配置。

## 五、需求明细

### 5.1 入口与导航

1. 导航项「更新 CLI」，图标用原生 `IconDownloadOutlineRegular` 20px，位置在「智能体设置」之后、「CLI 连接」之前。
2. 有可更新的 CLI 时，在导航项右侧显示数量徽标（数量来自缓存，打开设置窗口时就有，不必先进本页）：高 18px，12px 500 强调色字，底色为 12% 强调色混合；数量为 0 时不显示。

### 5.2 页面结构与状态

1. 页头：不放图标（2026-11-13 你在设计稿上删掉），24px/32px 600「更新 CLI」、12px 三级色副标题「检查、更新或安装这台电脑上的 CLI」；右侧为一组页级操作，间距 8：md outline「检查更新」（带刷新图标，检查中改为转圈加「正在检查」并禁用），其右为页内唯一的 md primary「全部更新」（2026-11-13 你在设计稿上指出放在分区标题行里突兀，移到页头）；没有可更新的 CLI 时不显示「全部更新」，有操作进行中时置灰。
2. 页头下不放状态行（不显示「上次检查」「共 N 个 CLI」「正在检查 / 更新 / 安装」等文字，2026-11-13 你在设计稿上删掉）。页头到第一个分区标题的间距与「CLI Worker 设置」通用页相同：页头最小高 60（含上内边距 4），其后 28px（`.cwn-cli-identity+.cwn-settings-section`）。检查进度由「检查更新」按钮的转圈和「检查中」分区表达；更新、安装进度只在对应行内显示。
3. 分区按顺序排列，没有内容的分区不显示。每个分区标题行最右侧都有同一个折叠按钮（36×36 ghost 图标按钮，原生 `IconChevronDownOutlineRegular`，收起时旋转 -90°；2026-11-13 你在设计稿上要求全部统一）。默认「未安装」收起，其余展开；收起状态按分区记在本机：
   - **检查失败**：说明原因（连不上发布源、读不出当前版本等），右侧为「重试」；读不出版本时为「去设置路径」（跳到对应 CLI 连接页）和「重新安装」（装到默认位置，见 5.11 第 6 条）。
   - **可更新**：标题行只有标题、数量和折叠按钮；「全部更新」放在页头（见第 1 条）。
   - **需要手动更新**：桌面应用托管、包管理器不受支持（WinGet、Scoop、Nix、Bun、pnpm 全局等）、或识别不出安装来源的 CLI。
   - **已是最新**：默认展开。
   - **未安装**：默认收起，标题带数量；有安装正在进行时自动展开。每行说明安装方式和前置条件，右侧为「安装」（见 5.11）。
   - **下载设置**：固定在页面最后，默认展开，只有「下载源」一项（见 5.12）。
4. 每一行：32px 品牌图标（圆角 8，与右侧名称加说明两行等高，2026-11-13 你在设计稿上要求放大），间距 12，CLI 名称（14px/22px）；下方 12px/18px 三级色说明，写版本和安装来源，例如「0.129.0 → 0.130.0 · npm 全局安装」。右侧为操作按钮。行上下留白 16px，行间只有一条 0.5px 分隔线。
5. 首次打开时，按 5.4 的检查时机自动检查；检查过程中的页面更新按 5.2.1 执行。

### 5.2.1 加载与刷新时的页面更新（2026-11-13 你要求考虑清楚）

原则：先给可用的内容，结果先写在原行，分区归类集中重排，整个过程最多重排两次；不清空已有内容，不画空白骨架页，不让正在看的位置跳动。

有后台预加载（5.13）后，平时打开页面都属于第 2 种情况，直接显示；第 1 种只在插件第一次安装、缓存被清空、或 DSH 刚启动而预加载还没开始时出现。

1. **没有任何缓存（插件第一次安装、缓存被清空，或预加载还没开始）**
   - 第一步：页面打开时立即列出 17 个 CLI 的名称和图标（这些是插件自带的，不需要等待），全部放在「检查中」分区，说明处转圈「正在读取当前版本…」。页头「检查更新」变为转圈「正在检查」并禁用，不显示「全部更新」；导航「更新 CLI」的徽标位置显示 12px 转圈。（画板 5）
   - Host 并发读取本地安装与当前版本，每个 CLI 最多 5 秒，超时记为「读不出版本」。全部读完后**重排第一次**：未安装的收进「未安装」（默认收起），读不出版本的进「检查失败」，其余留在「检查中」，说明改为「<当前版本> · 正在查询最新版本…」。
   - 第二步：查询官方发布源，每个最多 8 秒、3 个并发。每个 CLI 的结果出来后**只改写原行的说明和按钮，不移动位置**，例如 Codex 变成「0.129.0 → 0.130.0 · npm 全局安装」并出现「更新」，OpenCode 变成错误色「连不上发布源」。（画板 13）
   - 全部查完后**重排第二次**：按可更新、需要手动更新、已是最新、检查失败归类，「检查中」分区消失；「全部更新」出现，导航徽标改为可更新数。
2. **有上次结果（缓存）**
   - 打开页面直接按上次的分区显示，不清空、不闪骨架。最新版本距上次查询不到 6 小时就不查，页面保持静止。
   - **只有部分 CLI 有缓存**（预加载做到一半、刚装了新 CLI、某个 CLI 的可执行文件变了）：有缓存的行照常按分区显示；没有的行放进「检查中」分区（位置在「检查失败」之前），只对这些行按第 1 种的两步读取，读完后与其他行一起**重排一次**。已有结果的行不重读。
   - 打开页面时预加载正在进行：页面接上同一个任务，不重复启动探测；剩下的 CLI 立即改为前台速度（并发与超时同第 1 种），不再等系统空闲。
   - 超过 6 小时或用户点「检查更新」时，每一行原地在说明前加转圈「…· 正在重新检查」，查完的行去掉转圈、改写说明；全部查完后**统一重排一次**。检查期间「全部更新」置灰；行内「更新」仍可用，开始前 Host 重新生成计划并核对指纹。（画板 14）
3. **重排时的保护**
   - 用户展开着的行（查看方法、安装位置、命令输出）和正在更新、安装的行，原地不动，等收起或操作结束后下一次重排再归类（与 5.7 第 4 条一致）。
   - 重排前记下当前视口内第一行，重排后把滚动位置对回这一行，避免内容整体跳动；若这一行移到了别的分区，则对回它所在的新位置。
   - 没有内容的分区隐藏；分区顺序固定，不因结果先后改变。
   - 已收起的分区保持收起，只更新标题里的数量。
4. **慢与失败**
   - 某个 CLI 一直没有结果时，不拖住其他行：第二步总等待上限为 30 秒，超时的行写「查询超时」，随第二次重排进「检查失败」。
   - Host 整体读不到状态（Gateway 不通、插件刚启用）：整页只显示一行原因和 md outline「重试」，不显示空分区。
   - 检查进行中关闭窗口或切换页面，Host 继续检查；回来时直接显示 Host 当前的阶段与已有结果，按同样规则继续。
5. **无障碍**：检查中的分区设 `aria-busy`；每次重排后用 status 区域播报一次结果（如「检查完成：3 个可更新，1 个检查失败」），不逐行播报。

### 5.3 安装来源识别与更新方式

1. 根据插件实际调用的可执行文件路径（自动识别或用户自定义的路径）解析符号链接，再按以下顺序识别安装来源：
   - Homebrew（路径含 `Cellar/` 或 `Caskroom/`，且包名与该 CLI 的 formula/cask 一致）→ 用同一前缀下的 `brew upgrade <包名>`；
   - npm 全局包（路径含 `lib/node_modules/<包名>/`；Windows 为 `node_modules/<包名>/`）→ 在原前缀下更新该包（`--prefix <原前缀>`），不换包管理器；
   - CLI 自带更新命令（如 `claude update`），且官方说明该命令适用于当前安装方式 → 执行自带命令；
   - 官方独立安装器装出的版本 → 用官方安装器更新到原目录（第九节第 5 条你已定：自动执行，只限 Host 内置的官方地址）；
   - WinGet、Scoop、Nix、Bun、pnpm 全局、桌面应用内置运行时 → 只给官方方法，不自动执行；
   - 以上都不匹配 → 归入「需要手动更新」，说明「没有识别出安装方式」。

### 5.4 版本检查

1. 当前版本由 Host 执行 `<CLI> --version`（或该 CLI 已有的版本读取方式）获得，带超时；Kimi 探测必须设置 `KIMI_CODE_NO_AUTO_UPDATE=1`，避免探测本身触发 Kimi 的自动升级（当前源码尚未设置，实施时先补）。没有可靠无副作用读法的 CLI 显示「版本未知」，不硬跑。
2. 最新版本只从官方发布源读取（npm registry、Homebrew API、官方 manifest），每个请求 8 秒超时，最多 3 个并发，响应体超过 512 KiB 视为无效；不带任何凭据。
3. 版本按 SemVer 比较。当前是正式版、远端是预发布版时，视为不同发布通道，不提示更新。版本读不出时显示「版本未知」，不猜。「最新版本」与「插件已适配的最新版本」分开：Pi（白名单 1.0.2 / 1.0.4 / 1.1.0）、OpenCode（V1 与新世代不能混用）等，发布源上的新版本超出适配范围时，行内写「有新版本 X，插件尚未适配」，不提供更新按钮。
4. 检查时机（第九节第 7 条你已定）：DSH 启动后由后台预加载检查一次（5.13）；打开本页时，最新版本超过 6 小时的就地重查；其余时间只在用户点「检查更新」时检查。不设反复的定时检查。
5. 检查结果存在 Host 内存和插件私有缓存中（目录 0700、文件 0600），分层与失效规则见 5.13；重开设置窗口、重启 DSH 后都先用这份结果显示（见 5.2.1 第 2 条）。

### 5.5 执行更新

1. 用户点「更新」后直接开始，不再弹确认框（第九节第 2 条你已定）。展开区依次显示：下载进度（能获取时）、实际执行的命令（等宽字体、可复制）和命令输出。
2. 全局同一时间只执行一个更新；其他行的「更新」与「全部更新」按钮置灰，悬停提示「一次只更新一个 CLI，<CLI> 完成后再更新」。Host 侧同样加锁，不依赖前端。
3. 「全部更新」按「可更新」分区的顺序逐个执行；某一个失败后继续下一个；结束后不另做汇总，每个 CLI 的结果留在各自行内。
4. 有 Worker 正在使用该 CLI（运行中、排队中、停止清理中）时，不能更新：按钮置灰，说明「有 N 个任务正在使用」，悬停提示「这些任务结束或停止后才能更新」。更新期间，该 CLI 不接收新派遣、续聊、账号登录窗口与模型目录查询，提示「<CLI> 正在更新」；这把锁在 Host 侧实现，不只是前端置灰。
5. 命令只用参数数组执行，不经 shell 拼接；Windows 下 `npm` 调用 `npm.cmd` 时同样不拼字符串。不附加插件自己的系统沙箱。
6. 输出只保留最后 32 KB，去掉 ANSI 控制序列，按纯文本显示（不渲染 HTML），并对令牌、`Authorization` 头和 URL 中的凭据做脱敏。
7. 可以取消。取消后终止整个进程树，等进程确实退出后才显示「已取消」；已写入的文件不回滚，说明中写明并建议重新检查。
8. 关闭设置窗口或切换页面不影响更新；重新打开时从 Host 读取当前状态并恢复显示。插件停用或 Host 退出时终止更新，并清理进程。

### 5.6 下载停滞检测与断点续传

1. 下载进行中每 10 秒检查一次进度。10 秒内已下载字节没有增长，就暂停（中断当前连接或进程），再从中断处继续；最多循环 200 次，超过后判为失败：「下载停在 X / Y，自动续传 200 次仍没有进展。检查网络后重试」。
2. 插件自己能掌控下载的方式（npm 包的 tarball、官方安装包或二进制）：先下载到插件私有缓存目录（0700），用 HTTP Range 从已下载字节处续传；服务器不支持 Range（返回 200 而非 206）时，从头重新下载，同样计入 200 次。下载完成后按发布源给出的 integrity（sha512）或长度校验，校验失败就删掉临时文件，判为失败。再用本地文件安装（如 `npm install -g <本地 tgz> --prefix <原前缀>`）。
3. 插件无法掌控下载的方式（CLI 自带更新命令、`brew`、官方安装脚本，以及 npm 主包之外的依赖下载）：只有能确认处在下载阶段、并能读到属于本次操作的下载文件字节时，才按 10 秒规则判断；没有增长就终止进程树，确认退出后重跑同一条命令，同样计入 200 次。命令只是 10 秒没有输出不算停滞；正在解压、编译、替换文件的阶段不中断。读不到下载字节时，行内写「正在执行，下载进度无法读取」，不画进度条、不显示续传次数，由安装阶段超时兜底。这类重跑是否真正续传取决于各工具自己的缓存，界面上记作「已自动重试 N 次」，与插件自己的「已自动续传 N 次」分开。
   - npm 包的说明：插件只接管主包 tarball 的下载（可 Range 续传、按 integrity 校验），依赖与平台二进制仍由 npm 下载，按上面的外部命令规则处理。
4. 界面显示「已下载 X / Y · 速度」和 4px 进度条；总大小未知时只显示已下载字节，不画百分比。续传次数显示为「已自动续传 N 次」，悬停说明规则；输出区同时记一行「下载停滞 10 秒，从 X 处续传（第 N 次）」。
5. 原来的「单次操作 10 分钟总超时」改为分阶段：下载阶段只受 10 秒停滞和 200 次上限约束（200 次停滞至少约 33 分钟，10 分钟总超时会提前截断）；安装阶段单独计 10 分钟。另加下载总时长上限 2 小时（第九节第 13 条，你已定），超出判为「下载超时」，与「续传 200 次仍失败」分开提示。
6. 临时文件在成功、失败、取消后都删除；失败或重启后的保留期限见第九节第 14 条，Host 启动时清理过期的临时文件。
7. 服务器不支持续传、返回 200 时从头覆盖重下，绝不追加到旧文件；返回 206 时核对 Content-Range 起点。校验失败允许干净重下一次，仍失败就判为「下载的文件校验不通过」，不耗尽 200 次。404、权限或证书错误等不可恢复错误直接失败。
8. Host 重启或插件停用时，进行中的操作记为「已中断」，不自动重跑；用户重新点击后沿用已用掉的次数。

### 5.7 结果核对

### 5.11 安装未安装的 CLI

1. 入口：「未安装」分区每行一个 md outline「安装」。之前记录的路径已找不到文件时，该 CLI 归入「未安装」，说明「之前记录的路径 <路径> 已找不到」；文件还在但读不出版本的，留在「检查失败」，提供「重新安装」。
2. 纯 CLI 一律装到官方默认位置，不提供位置选择：
   - 安装方式按官方推荐；官方同时推荐多种时，优先插件能掌控下载的官方 npm 包（可 Range 续传、按 integrity 校验），其次官方安装脚本（第九节第 5 条你已定：自动执行，只限 Host 内置的官方地址），都不可行时只给官方说明。按 5.3 表，多数 CLI 的官方首推是安装脚本，只有 CodeBuddy Code 与 MiMo Code（Windows）以 npm 为主，所以第九节第 5 条定为自动执行后，大部分 CLI 才能在本页安装。每个 CLI 用哪种方式写在 5.3 表的「安装方式」列。
   - npm 包装进当前 `npm prefix -g` 指向的全局目录；目录不可写时不提权（不用 sudo），说明原因并给官方说明。官方脚本装到脚本自己的默认位置（如 `~/.local/bin`）。
   - 行内显示「安装到 <路径>」，路径在开始前由 Host 算出，不在页面上让用户改。
3. 带官方桌面客户端的 CLI（ZCode、WorkBuddy CN、WorkBuddy）可以选安装位置：
   - 点「安装」先在行内展开位置气泡：默认值为官方安装程序的默认目录（macOS `/Applications`，Windows 以官方安装程序为准，待核实），可改成其他目录，「恢复默认位置」一键还原。输入框右侧为 36×36 md outline 文件夹图标按钮（只有图标，无障碍名称和悬停提示为「浏览文件夹」），点击直接打开系统的选择文件夹窗口，不给预设位置（2026-11-13 你在设计稿上要求）；DSH Desktop 能否从插件调起系统窗口待核实，不能时改为插件自绘的文件夹浏览，由 Host 只列目录、不读文件。也可以直接在输入框里改路径。

   - 装好后，插件在所选位置找到 CLI 入口，写入本机路径记录（与「CLI 连接 › 高级设置 › CLI 路径」同一处），用户不用再填路径。
4. 前置条件先查，不满足就不装，具体见 5.3 表「前置条件」列：npm 路线需要 Node.js（如 Kimi、Pi 为 22.19，Claude Code 为 22，CodeBuddy Code 为 18.20，MiMo Code 为 18），官方脚本路线多数不需要预装 Node；OMP 的 Bun 路线需要 Bun 1.4.4 及以上（以目标版本为准）；Kimi 在 Windows 需要 Git Bash；Hermes 需要 Git、curl、tar；TRAE CN 需要能直连 trae.cn（返回 403 时说明是地区限制）。Pi 只能安装插件已适配的版本。说明里写当前版本和所需版本，「安装」置灰并给「官方说明」。插件不代装 Node.js、Bun 等运行时。
5. 执行与更新相同：纯 CLI 点「安装」直接开始；与更新共用全局锁（一次只做一个安装或更新）；下载 10 秒无增长就从中断处续传，最多 200 次；可取消，进程树确实退出后才显示已取消；关闭窗口后在后台继续；输出截断与脱敏规则相同。
6. 结果核对：退出码为 0 后重新探测，读得出版本才算成功，显示「已安装 X，登录后即可派遣」和 md outline「去登录」（跳到「CLI 连接 › 该 CLI」的账号区）。探测不到时显示「安装命令已完成，但在 <路径> 找不到 <CLI>」，给「查看输出」「官方说明」「重试」。重新安装成功后，插件改用新位置，旧文件不删除，说明里写出旧位置。
7. 不做：全部安装、卸载、安装运行时（Node.js、Bun）、选择纯 CLI 的安装位置。

### 5.12 切换下载源

1. 位置：页面最后的「下载设置」分区，与其他分区用同一种标题行和折叠按钮。只有一行设置「下载源」，左侧是 14px 标签和 12px 三级色说明「npm 包从哪里下载。官方安装脚本、Homebrew 和桌面安装包不受影响」，右侧是下拉选择（沿用插件 `NativeChoice`：高 36、圆角 12、0.5px 描边、原生下拉箭头，与「CLI 连接」页的模型、强度选择一致；最小宽 208）。
2. 选项（下拉菜单宽 360，每项主行加一行三级色说明，选中项打勾）：
   - **跟随 npm 设置**（默认）：使用这台电脑 npm 配置里的源，说明里写出当前地址。公司内部源用户不需要改任何设置。
   - **npm 官方源**：`registry.npmjs.org`。
   - **国内镜像**：npmmirror（`registry.npmmirror.com`）。
   - **自定义地址…**（分隔线下）：选中后在该行下方 16px 展开「源地址」输入框，输入框到操作行 8px；只接受 https，地址里不能带用户名或密码；操作行左侧显示检查结果（如「连接正常 · 0.4 秒」或错误色原因），右侧为 sm outline「检查连接」。
3. 作用范围：只影响插件发起的 npm 安装和更新（包括插件自己下载的主包 tarball 和 npm 后续下载的依赖），以参数数组形式传 `--registry <地址>`，不改用户的 `.npmrc` 或全局 npm 配置。官方安装脚本、CLI 自带更新命令、Homebrew、桌面安装包始终从官方下载。
4. 可信度：使用镜像或自定义源时，最新版本号和 `dist.integrity` 优先向 npm 官方源核对，官方源连不上时才采用所选源给出的值，并在行内命令下方注明「校验值来自 <源>」；下载内容与 integrity 不符一律判为失败，不安装。
5. 行内体现：使用非官方源时，展开区里的命令显示实际的 `--registry` 参数，说明中写「npm 全局安装 · 国内镜像」。npm 下载续传失败或停滞次数较多时，失败说明中加一句「可以在页面底部切换下载源后重试」（链接滚动到该设置），不自动替用户切换。
6. 设置保存在 Host 插件私有配置（目录 0700、文件 0600），按本机保存，不同步到其他电脑；切换后从下一次安装或更新开始生效，不影响正在进行的操作。

### 5.13 后台预加载与缓存（2026-11-13 你要求）

目标：用户打开「更新 CLI」页或「CLI 连接」页时，CLI 的版本、安装来源和账号登录状态已经在缓存里，直接显示，不再等加载。

1. **何时开始**：插件 Host 随 DSH 启动后，先等 60 秒（避开 DSH 自身启动、恢复会话最忙的时段），再检查系统是否空闲；空闲才开始，否则每 30 秒再看一次。每次 DSH 启动只完整跑一遍，不做反复的定时检查。
2. **怎样算空闲**（第九节第 18 条你已定）：
   - 没有 Worker 任务在运行或启动中，没有打开的登录窗口，没有更新或安装在进行；
   - 系统 CPU 忙碌低于 50%：用 `os.cpus()` 前后两次的时间差采样 2 秒算出，macOS 和 Windows 通用（Windows 上 `os.loadavg()` 恒为 0，不能用）。
3. **怎样保持低负载**：
   - 同一时间只跑一个探测，每项之间至少间隔 2 秒；
   - 探测用的子进程调低优先级（macOS nice 10；Windows BELOW_NORMAL），超时与前台相同；
   - 用户一派遣任务、打开登录窗口或开始更新、安装，预加载立刻暂停，正在跑的那一个探测按原生方式取消并确认进程退出；之后系统再空闲 30 秒才接着做，从没做完的那一项继续；
   - 网络请求（查询最新版本）不带凭据，单个失败就记为失败、留到打开页面时再查，不重试、不弹提示。
4. **读什么、按什么顺序**（越便宜越先做，前一类全部做完再做下一类）：
   - ① CLI 路径：只核对已记住的路径还在不在（`stat`，不启动进程），不重新搜索；
   - ② 当前版本：只给指纹变了或没有记录的 CLI 运行 `--version`（指纹见第 5 条）；
   - ③ 账号登录状态：只读已启用的 CLI，调用与设置页相同的只读状态读取；会刷新令牌、改写 CLI 配置或打开窗口的读法，后台一律跳过，留到打开设置时再读；
   - ④ 最新版本：超过 6 小时的才查，查询规则同 5.4 第 2 条，使用所选下载源；
   - ⑤ 模型目录：沿用已有的磁盘缓存（`settings-catalog-cache`），后台只补没有缓存的 CLI。
5. **缓存分层**（插件私有目录，目录 0700、文件 0600，按本机保存，不入 Git）：

| 数据 | 保存多久 | 什么时候重读 |
|---|---|---|
| CLI 路径 | 长期（沿用已有的每机路径记录） | 文件不存在或不可执行、用户改了手动路径、本页刚装完或更新完 |
| 安装来源（npm、Homebrew、官方脚本、桌面应用等） | 长期 | 可执行文件真实路径变了 |
| 当前版本 | 长期 | 指纹变了：真实路径、文件大小、修改时间（桌面应用再加应用包的版本号）任一不同 |
| 最新版本 | 6 小时 | 超时、用户点「检查更新」、换了下载源 |
| 账号登录状态 | 长期保留上次结果用于显示 | 超过 10 分钟的，打开设置时原地静默重读（第九节第 19 条你已定）；登录、退出、切换账号后立即重读 |
| 模型目录 | 沿用现有规则 | 沿用现有规则 |

6. **只存显示需要的内容**：版本号、来源、分区、检查时间、账号的登录状态和界面上本来就显示的账号名；不存令牌、Cookie、API Key、命令输出。缓存文件读不出或格式不对就整份丢弃，按没有缓存处理，不报错。
7. **账号状态与项目有关**：Qoder、TRAE CN、WorkBuddy 等 CLI 的账号状态按项目目录读取。后台预加载用最近一次打开设置时所在的项目；换到别的项目打开设置时，这几项按第 5 条视为过期，原地重读。
8. **有副作用的探测不在后台跑**：Kimi 必须带 `KIMI_CODE_NO_AUTO_UPDATE=1`；其他 CLI 的 `--version` 是否会自动升级、写配置或联网，实施时逐个验证，标为后台可用后才放进预加载；没验证的保留上次结果或显示「版本未知」，等用户打开页面再按前台方式读。
9. **页面怎么用缓存**：见 5.2.1 第 2 条。缓存和 Host 当前阶段由 Host 一次返回，Client 不自己存。「检查更新」按钮悬停时显示「上次检查：<时间>」，页面上不加状态行。
10. **开关**（第九节第 20 条你已定）：「CLI Worker 设置」通用页加一个开关「启动后在后台检查 CLI」，默认开。关掉后不做预加载，打开页面时按 5.2.1 加载。
11. **生命周期**：预加载的定时器、采样器和子进程都登记在插件生命周期里；插件停用、DSH 退出时全部取消，子进程确认退出后才算清理完成。预加载从不占用 5.5 的更新锁，也不阻止派遣。

**能做到与做不到**：

- 能做到：平时打开页面直接显示，不出现「检查中」；路径不再重新搜索；版本只在可执行文件变了时才重读。
- 做不到「每次都零加载」的情况：插件第一次安装或缓存被清空；DSH 启动后 60 秒内（还没开始）或系统一直繁忙时打开；用户在终端里自己更新或重装了 CLI（指纹变了，那一行会在打开时重读 1～5 秒）；换项目后与项目有关的账号状态。这些情况都只加载缺的部分，见 5.2.1 第 2 条。

## 七、风险与依赖

1. 许可证：Codingns4DSH 为 GPL-3.0，本插件为 MIT。实现时不复制、不改写其源码，只参考公开文档和行为规则；PR 说明中写明参考来源。
2. 识别错误会装出第二份：用错包管理器或前缀，插件仍调用旧版本。对策是按真实路径识别、严格匹配包名，识别不出就转手动；更新后核对版本是否前进。
3. 官方安装脚本（`curl … | bash`、`irm … | iex`）会以用户身份执行远端脚本，风险高于包管理器。第九节第 5 条你已定自动执行，对策：只用 Host 内置的官方地址，先下载到私有缓存再以文件方式执行，行内显示脚本地址。
4. Kimi 探测会自动升级真实安装（已有记录）；检查和更新流程都必须设置 `KIMI_CODE_NO_AUTO_UPDATE=1`，当前源码尚未设置。
5. 断点续传依赖服务器支持 Range；npm registry 和部分 CDN 的行为需实测。包管理器自身的下载不受插件控制，只能「停滞后重跑」。
6. Windows：npm 全局前缀、`npm.cmd` 调用、进程树终止和文件占用（正在运行的 CLI 无法覆盖）都与 macOS 不同，需单独验收；Windows 系统代理需沿用插件已有的代理注入。
7. 更新期间如果用户在终端里直接运行同一个 CLI，插件无法阻止，可能导致文件占用而更新失败；失败时提示关闭后重试。
8. 安装：纯 CLI 只用官方默认位置，若该位置不在 Desktop 的 PATH 里，依赖插件已有的常见位置识别；装完找不到即判失败，不猜路径。桌面应用的静默安装参数、dmg 签名核对方式、默认目录逐个待核实；Windows 提权窗口在 Desktop 中不可见（已有记录），因此一律不走需要管理员权限的位置。
9. Pi、OpenCode 的最新发布版可能超出插件已适配的协议或版本白名单，盲目更新到 latest 会让插件拒绝启动该 CLI。
10. 外部更新命令的下载阶段难以识别，10 秒规则只能用在能读到下载字节的情况；其余情况只能显示进度无法读取。
11. 后台预加载会在用户不知情时启动 CLI 进程和访问网络。对策：只跑验证过无副作用的版本读取和只读账号状态，低优先级、一次一个、有任务就让路，并提供开关（5.13）。各 CLI 的 `--version` 是否有副作用，目前只确认了 Kimi，其余待逐个验证。
12. 缓存与真实情况不一致：用户在终端里退出账号、或用别的方式更新了 CLI，页面会先显示旧结果。版本靠文件指纹发现变化；账号状态靠打开时超过 10 分钟就重读，最长有 10 分钟的旧状态。
13. Windows 上 `stat` 和进程启动较慢，杀毒软件可能放大探测开销；Windows 的空闲判定和低优先级需单独验收。
