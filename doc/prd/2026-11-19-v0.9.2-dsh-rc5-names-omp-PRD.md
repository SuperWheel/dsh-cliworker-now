# v0.9.2：适配 DeepSeek Harness 0.2.2-rc.5，Agent 名称与 DSH 一致，「调用 DSH」派原生子 Agent，OMP 其他服务商图形化

- 来源：技术优化　类型：技术
- 问题：DeepSeek Harness 已于 2026-11-17 发布 0.2.2-rc.4、2026-11-18 发布 0.2.2-rc.5（npm dist-tag latest 与 next 均为 0.2.2-rc.5），本机 Mac 的 DeepSeek Harness Desktop 已更新到 0.2.2-rc.5。插件的开发 SDK 依赖、随包的四个原生界面包（ui-session、ui-conversation、ui-subagent、ui-chat）、构建与 vendor 脚本的目标仍锁在 0.2.2-rc.3。宿主与插件随包界面版本不一致，插件在 rc.5 宿主上的加载与运行没有经过验证，后续官方继续升级时落后幅度会扩大。
另有四个用户提出的问题：
1. 名称不一致：同一批 Worker 在 DSH 会话头部的子 Agent 列表里叫 agent-1 到 agent-6，在插件 CLI Worker 面板里叫 codex-1、agy-1、zcode-1；DSH 原生子 Agent 在插件里另编号为 dsh-N，在 DSH 里叫 agent-N。用户无法对照两处的同一个 Agent。
2. OMP 账号窗口的「其他服务商」只能在原生终端里配置；Pi、OpenCode、Hermes、ZCode 已经能在本窗口用图形表单填写。
3. 用户说「调用 dsh」「调用 DeepSeek Harness」时，插件没有把它识别为派遣 DSH 原生子 Agent：「deepseekharness」「harness」被当作已退役的外部 Harness CLI，提示改建 Hermes Agent 任务；「dsh」不被识别，写成「dsh cli」时还会被判为无法确定的 CLI 并列出候选。用户实测时主 Agent 说没有直接新建原生子 Agent 的工具，改用 workflow 的 agent() 绕行。
4. CLI Worker 面板中 DSH 原生子 Agent 分组的标题显示缩写「DSH」，与其他分组使用产品全称（Antigravity、Codex、ZCode 等）不一致。

## 一、背景与问题

1. 插件 package.json 的 39 个 @deepseek-ai/dsh* 开发依赖精确锁定 0.2.2-rc.3；scripts/host-targets.json 的 vendorDefault 为 0.2.2-rc.3；runtime-host/ 中四个随包界面包按 rc.3 源码加 48 个文件的补丁构建。
2. 官方 tag dsh-v0.2.2-rc.4 = 3f321d32bf，dsh-v0.2.2-rc.5 = 9c2670d3bc，均为 rc.3 的后代。rc.3..rc.5 共 448 个文件改动（多数为 package.json 与 CHANGELOG 版本号）。
3. 实质改动集中在：联网搜索默认服务随模型路由选择（web、web-search-deepseek、tool-web、ui-settings-web-search，WebSearchRequest 新增可选字段 llmProvider）；DeepSeek 内容安全检查与拒答（llm-deepseek，LLM_FAILURE_CODES 新增 CONTENT_REFUSED）；liveshare 隧道在 Electron Node 模式启动；bundle/base 的 cordis.patch.yml 调整。
4. 插件随包的四个界面包在 rc.3..rc.5 之间只有 package.json 版本号变化；插件源码不引用上述变动的接口（初步检索 src/ 无 LLM_FAILURE_CODES、WebSearchRequest、liveshare 引用）。完整的已安装 npm 包逐包差异待实施时核对。
5. 插件当前在 rc.5 Desktop 上能否正常加载、派遣与续聊：待核实。
6. 名称来源：DSH 从 0.2.2-rc.2 起给子 Agent 命名（packages/subagent/subagent/src/names.ts），建子会话时可传入 name，不传则取第一个空闲的 agent-N；名称须为 1–32 位小写字母、数字或连字符，以字母开头，不能是 lead，同一父会话下唯一；DSH 未提供改名接口：子 Agent 名称记录在父会话日志的 subagent/catalog 事件中，只追加、写入后不可变，退役或结束的子 Agent 名称也永久占用（Fable 2026-11-19 调研，tag dsh-v0.2.2-rc.5 的 subagent 包只有 prompt 与 interruptByUser 两个 Remote）。插件的 Worker 子会话走 DSH 的本地子会话路径（startLocal），可以在创建时传入名称。第二轮调研：名称的唯一来源是 subagentCatalog 投影，投影注册先到先得，插件无法覆盖或包装；会话日志的插件记录接口禁止仓库外插件调用；DSH 公开了工具执行前、执行中、执行后三个钩子（tools/pre-execute、tools/execute、tools/post-execute）。CLI Worker 的 CLI 会话与缓存挂在 Worker 上，DSH 侧名称不进入 CLI 上下文；DSH 原生子 Agent 的名字在每步重算的运行期上下文中，改名只追加一条上下文消息，不破坏前缀缓存。插件建 Worker 子会话（src/host/harness-conversation.ts 的 create）时不传 name，所以 DSH 自动编号为 agent-N。插件自己的名称（agentName）最长 60 字、可含中文，并支持改名。
7. 插件对 DSH 原生子 Agent 另行编号 dsh-N，持久化在 dsh-names.json（src/host/dsh-subagents.ts），没有读取 DSH 目录里的名称。
8. 其他服务商图形表单（src/host/custom-provider.ts，变更 vnext-custom-provider-form-leeyl 归档）目前只支持 Pi、OpenCode、Hermes、ZCode。当时 OMP 18.20.0 返回 null 继续走原生终端，原因是凭据存于 agent.db 的 auth_credentials 表，原生 auth import 为合并操作、没有核实可撤销的单项写入方式。插件读取 OMP 配置时已识别 models.yml 中 providers 的 apiKey 字段，说明不经 agent.db 写入凭据有可能可行（待按 OMP 当前版本 18.22.0 核实）。
9. 「调用 X」识别：src/host/routing.ts 的 invocationResolution 只识别 CLI 名称；resolveCliName 把规范化后的 harness 与 deepseekharness 判为 retired，invocationHint 注入 RETIRED_HARNESS_NOTICE（「外部 Harness CLI 入口已移除…请新建 Hermes Agent 任务」）。DSH 基础包默认装载原生子 Agent 委派工具 subagent（spawn 后端）与 subagent_fork（cordis.patch.yml 中的 tool-subagent、tool-subagent-fork），子 Agent 结果回到主对话后由插件汇入 CLI Worker 面板的 DSH 分组。用户实测会话中主 Agent 称工具列表没有直接新建原生子 Agent 的工具，原因（当前 Agent 预设是否装载 subagent 工具）待核实。
10. 分组标题：src/client/panel.tsx 第 728–731 行把 DSH 原生子 Agent 分组的标题与无障碍标签写死为「DSH」。

## 二、目标用户与使用场景

1. 使用 DeepSeek Harness Desktop 0.2.2-rc.5 的插件用户：Desktop 自动更新到 rc.5 后，希望 CLI Worker 面板、设置、派遣、续聊、停止与审批照常可用。
2. 插件维护者：开发、测试与构建以宿主最新版本为准，避免在旧 SDK 上开发、在新宿主上运行。
3. 同时看 DSH 会话头部子 Agent 列表和插件 Worker 面板的用户：需要按同一个名称对照、续聊与停止同一个 Agent；主 Agent 按名称续聊时，DSH 与插件的名称指向同一个 Agent。
4. 使用 OMP 接入自有 API Key 服务商的用户：希望像 Pi、OpenCode 一样在账号窗口里直接填写，不切到原生终端。
5. 想把任务交给 DeepSeek Harness 自己的子 Agent 的用户：说「调用 dsh」「用 DeepSeek Harness 做…」时，希望主 Agent 直接派 DSH 原生子 Agent，而不是被引导去选外部 CLI 或 Hermes。

## 三、目标与成功指标

1. 插件的开发 SDK、随包原生界面与构建目标跟随 DeepSeek Harness 0.2.2-rc.5，在 rc.5 宿主上加载与核心流程通过验收；若差异核对确认无破坏性变化，不改插件业务代码。
2. 每个 Worker 和 DSH 原生子 Agent 在 DSH 子 Agent 列表与插件面板中显示同一个名称，改名后两边仍一致。
3. 用户说「调用 dsh」「调用 DeepSeek Harness」等时，主 Agent 派遣 DSH 原生子 Agent 执行任务，结果出现在面板的 Deepseek Harness 分组；分组标题显示 Deepseek Harness。
4. OMP 的「其他服务商」与 Pi、OpenCode、Hermes、ZCode 一样可在账号窗口的图形表单中填写保存。
成功指标：插件锁定的 DSH 版本从 rc.3 升到 rc.5；新建 Worker 两边名称不一致的数量为 0；「调用 dsh」类指令派遣到原生子 Agent 的比例为 100%；OMP 添加其他服务商不再需要打开原生终端。

成功指标：其他（无数值基线）

## 四、方案概述

1. 固定来源：记录 npm 发布时间、官方 tag 与 commit、本机 Desktop 版本。
2. 差异核对：对比 rc.3 与 rc.5 的源码和已安装 npm 包，覆盖 Gateway、Remote、扩展点、主题 token、共享组件、四个随包界面包与 Cordis 版本，结论写入 OpenSpec 设计；有破坏性变化时按结果适配。
3. 依赖升级：39 个 @deepseek-ai/dsh* 精确版本升到 0.2.2-rc.5，pnpm-workspace.yaml 发布期限例外同步；构建依赖选择与 host-targets.json 加入 rc.5 目标，vendor 默认改为 rc.5。
4. 重建随包四包：在 rc.5 tag 上应用现有 48 个文件的补丁（ui-subagent 另加名称覆盖层的页头列表改动），冻结独立构建依赖，构建、校验并重新 vendor runtime-host/；跑上游四包 Vitest。
5. 验证与文档：类型检查、全量测试、隔离预览包、隔离 DSH_HOME 端到端、Mac Desktop 实机加载与真实派遣；同步 README（中英）、doc/design.md 与原生会话宿主扩展协议文档中的宿主版本说明。
6. 在独立 worktree 中实施，验收通过后合并到 main，随 v0.9.2 发布（2026-11-19 用户确认版本号）。
7. Agent 名称一致：建 Worker 子会话时把插件名称作为 name 传给 DSH；插件自动命名、自定义命名与改名统一按 DSH 规则校验，不合规时当场提示；DSH 原生子 Agent 直接显示 DSH 目录里的名称，不再另编 dsh-N。改名采用「名称覆盖层」（2026-11-19 用户选定），子 Agent 的会话、历史与运行状态都不动，运行中也能改：插件内部只有一个改名入口，先探测 DSH 是否提供 subagents.rename，有则直接调用，没有则写插件私有的覆盖表（父会话 → 子 Agent → 现名与曾用名，存插件存储，不写会话日志）。覆盖表在四处生效：插件面板与 cliworker_followup；随包补丁版 ui-subagent 的页头列表；tools/execute 钩子让主 Agent 的 send_message、interrupt_agent 能按新名称寻址；tools/post-execute 钩子把 list_agents 输出中的原名换成新名；tools/pre-execute 拦截主 Agent 新建子 Agent 时占用覆盖表中的名称。曾用名保留为别名，主 Agent 上下文里的旧名称仍可用，不必通知。存量 Worker 直接采用 DSH 已有名称，原插件名称作为曾用名。同时向 DSH 官方提出原地改名接口（subagent/rename 事件、曾用名保留为别名、运行期路径同步、rename 服务方法与 Remote）；官方提供后，插件启动时把覆盖表逐条迁移到官方接口。不随包替换 DSH 子 Agent 后台包，不改 DSH 持久化数据。
8. OMP 其他服务商：核实 OMP 18.22.0 的 models.yml 服务商定义（providers、baseUrl、api、models、apiKey）与凭据写入方式，复用现有其他服务商表单（provider-form.tsx、custom-provider.ts 的票据、事务写入与回滚），写入插件 OMP 账号目录，不改 OMP 全局配置；保存后刷新账号与模型目录。
9. 「调用 DSH」：在 routing.ts 增加 DSH 原生子 Agent 这一目标，别名至少包括 dsh、DeepSeek Harness、deepseekharness、harness、DeepSeek Harness 原生子 Agent，大小写与空格不敏感；识别后注入提示，要求主 Agent 用 DSH 原生子 Agent 工具（subagent）派遣并传入任务，不调用 cliworker_start、不走 CLI 选型；与外部 CLI 同时出现时分别处理。harness/deepseekharness 不再提示已退役，旧外部 Harness CLI 的历史记录仍按只读处理。核实主 Agent 当前预设是否装载 subagent 工具；未装载时提示用户在 Agent 设置中启用，不改用 workflow 绕行。
10. 分组标题：DSH 原生子 Agent 分组的标题与无障碍标签改为「Deepseek Harness」（2026-11-19 用户指定此写法，s 小写），图标与计数不变。

## 五、需求明细

### 1. 固定来源与差异结论

系统应当记录 rc.4、rc.5 的 npm 发布时间与官方 tag commit，并给出 rc.3 到 rc.5 对插件影响的逐项结论（Gateway、Remote、扩展点、主题 token、共享组件、随包四包、Cordis）。

- 当查看本次 OpenSpec 变更的设计与任务记录，那么能看到 tag dsh-v0.2.2-rc.5 对应 commit 9c2670d3bc、逐包差异清单，以及「需适配」或「无需改动」的结论和依据

### 2. 开发依赖升级到 rc.5

系统应当把全部 @deepseek-ai/dsh* 开发依赖精确锁定到 0.2.2-rc.5，非 DSH 依赖保持不变。

- 当执行 pnpm install --frozen-lockfile，那么安装成功，锁文件中非 DSH 包集合与升级前一致
- 当执行 pnpm typecheck，那么输出 Host/Client typecheck passed against DSH 0.2.2-rc.5

### 3. 随包原生界面跟随 rc.5

系统应当基于 rc.5 源码重建 ui-session、ui-conversation、ui-subagent、ui-chat 四个随包界面包并 vendor 到 runtime-host/，补丁内容与 rc.3 一致或差异有记录。

- 当运行 build-host-extension --target 0.2.2-rc.5 --verify 与 vendor-host-extensions 复核，那么两项均通过，runtime-host 四包 package.json 版本为 0.2.2-rc.5，manifest 指向 rc.5
- 当运行上游四包 Vitest（补丁前后各一次），那么补丁后与补丁前同样全部通过，或失败项有根因与处理记录

### 4. 回归测试通过

系统应当在升级后通过插件现有全部测试，构建脚本与测试的目标版本改为 rc.5，旧目标的校验仍可运行。

- 当在 macOS 运行全量 vitest，那么失败为 0，通过数不少于升级前基线
- 当运行 pnpm lint 与 pnpm format:check，那么error 为 0，不新增 warning

### 5. rc.5 宿主实机加载与核心流程

系统应当在 DeepSeek Harness 0.2.2-rc.5 上正常加载插件，CLI Worker 面板、设置、派遣、续聊与停止可用。

- 当用隔离 DSH_HOME 安装预览包并启动 rc.5 自带的 dsh web，那么四个随包界面指向插件 runtime-host，主界面、CLI Worker 面板与设置页无白屏，控制台与 Host 日志无插件报错
- 当正式构建后在 Mac Desktop 0.2.2-rc.5 中让主 Agent 派遣一个已登录的 CLI 并续聊一次，那么选型卡片出现，Worker 终态为完成，产物与事件可核查，续聊沿用同一会话

### 6. Worker 名称与 DSH 子 Agent 一致

系统应当在为 Worker 建 DSH 子会话时使用插件名称，使 DSH 子 Agent 列表、插件 Worker 面板与主 Agent 按名续聊使用同一个名称；DSH 原生子 Agent 在插件中显示 DSH 目录里的名称。

- 当主 Agent 在一个会话中先后派遣 Codex、Antigravity、ZCode 各一个 Worker，那么DSH 会话头部子 Agent 列表显示 codex-1、agy-1、zcode-1，与插件 Worker 面板一致，不再出现 agent-N
- 当DSH 原生子 Agent 被 DSH 命名为 agent-6，那么插件 Worker 窗口中该子 Agent 也显示 agent-6，不再显示 dsh-N
- 当主 Agent 用 cliworker_followup 按名称续聊 codex-1，那么续聊到的是两边都叫 codex-1 的同一个 Worker
- 当同一会话中主 Agent 已用 DSH 工具建了名为 codex-1 的子 Agent，再派遣 Codex，那么插件避开 DSH 目录中已有名称，选用下一个未占用的名称，遇到 DSH 返回重名时换号重试，两边仍一致

### 7. 名称按 DSH 规则校验并支持改名

系统应当让插件的自动命名、自定义命名和改名都符合 DSH 名称规则（1–32 位小写字母、数字或连字符，以字母开头，不是 lead，同一父会话内不与任何子 Agent 的现名或曾用名重名），改名时子 Agent 不重建、不移动，只改变名称，并在插件面板、DSH 页头列表和主 Agent 的子 Agent 工具中一致。

- 当用户把 Worker 改名为含中文、大写字母、超过 32 位，或与同一会话中任何子 Agent（含已结束的、主 Agent 用 DSH 工具建的）的现名或曾用名重名的名称，那么保存前提示具体不合规的原因，名称不变
- 当用户把空闲或运行中的 Worker 改为合规的新名称，那么Worker 的 DSH 子会话 ID、历史和运行状态不变，没有新增子 Agent 条目；插件面板与 DSH 页头列表立即显示新名称
- 当改名后主 Agent 调用 list_agents，那么输出中该子 Agent 显示新名称
- 当改名后主 Agent 用新名称或旧名称调用 send_message 或 cliworker_followup，那么都送达同一个子 Agent
- 当改名后主 Agent 用 DSH 工具新建子 Agent 并指定该 Worker 的新名称或曾用名，那么创建被拒绝并提示名称已被占用
- 当Desktop 重启后打开该会话，那么插件面板与 DSH 页头列表仍显示新名称
- 当DSH 提供官方改名接口后启动插件，那么覆盖表中的改名逐条迁移到 DSH 目录，迁移成功的覆盖项删除，遇到冲突时保留覆盖项并提示
- 当升级前已存在、DSH 中显示为 agent-N 的 Worker，那么插件面板改为显示 DSH 中的名称，原插件名称作为曾用名仍可续聊，不重建子会话

### 8. 「调用 DSH」派遣原生子 Agent

系统应当把用户消息中的「调用 dsh」「调用 DeepSeek Harness」「用 deepseekharness / harness 做…」等直接指令识别为派遣 DSH 原生子 Agent，引导主 Agent 用 DSH 原生子 Agent 工具执行任务，不进入外部 CLI 选型，也不提示 Harness 已退役。

- 当用户在主对话发送「调用 dsh 帮我总结 README」，那么主 Agent 调用 DSH 原生子 Agent 工具派遣子 Agent 执行，不弹出 CLI 选型卡片；子 Agent 结果回到主对话，并出现在 CLI Worker 面板的 Deepseek Harness 分组
- 当用户发送「用 DeepSeek Harness 检查这个目录」「调用 deepseekharness …」「调用 harness …」「调用 dsh cli …」，那么同样派遣 DSH 原生子 Agent；插件不注入「外部 Harness CLI 入口已移除」或「无法确定 CLI」提示
- 当用户发送「调用 dsh 和 codex 分别审查这个模块」，那么主 Agent 派遣一个 DSH 原生子 Agent，并通过 cliworker_start 派遣 Codex，两者分别执行
- 当用户只是讨论（「dsh 的子 Agent 是什么」「调用 dsh 和 codex 有什么区别」），那么不派遣任何子 Agent
- 当主 Agent 当前预设没有装载 DSH 原生子 Agent 工具，那么主 Agent 告知用户需要在 Agent 设置中启用子 Agent 工具，不改用 workflow 或外部 CLI 代替

### 9. DSH 分组标题改为 Deepseek Harness

系统应当在 CLI Worker 面板中把 DSH 原生子 Agent 分组的标题与无障碍标签显示为「Deepseek Harness」。

- 当主对话中有 DSH 原生子 Agent 时打开 CLI Worker 面板，那么该分组标题显示 Deepseek Harness，图标与「N 个 Agent」计数不变，窄宽度下不截断成乱码或溢出
- 当切换为英文界面，那么分组标题同样显示 Deepseek Harness

### 10. OMP 其他服务商图形化配置

系统应当在 OMP 账号窗口的「添加账号」中提供「其他服务商（在本窗口中填写配置）」，复用现有其他服务商表单，保存到插件的 OMP 账号目录，不修改 OMP 全局配置。

- 当打开 OMP 账号窗口点添加账号，那么服务商卡片中「其他服务商」显示为在本窗口中填写配置，继续后进入与 Pi 相同布局的表单（服务商 ID、名称、Base URL、API 协议、API Key、模型 ID），并保留「在原生终端中配置」入口
- 当填写虚构测试服务商并保存，那么插件 OMP 账号目录中出现对应服务商与凭据，文件权限 0600；OMP 全局目录与已有服务商、密钥不变；OMP 账号状态与模型目录刷新后出现该服务商的模型
- 当服务商 ID 与已有服务商重名、字段为空或格式不对，那么逐字段提示错误，不写入任何文件
- 当写入中途失败，那么已写的文件回滚到写入前内容，提示失败原因
- 当OMP 当前版本无法核实安全的写入方式，那么表单不出现，继续使用原生终端，并在 OpenSpec 中记录原因

## 七、风险与依赖

1. 已安装 npm 包可能存在源码 diff 未体现的构建产物变化（类型声明、打包输出），需逐包 diff 已安装产物确认。
2. 构建四包需要从 GitHub 拉取源码与安装独立依赖，受代理与 DNS 影响可能需要重试；不移除宿主代理环境变量。
3. Windows Desktop 的 rc.5 安装包可能晚于 Mac 发布，Windows 验收时间依赖官方更新清单。
4. 真实派遣需要主对话模型余额与 CLI 登录可用；不可用时记录为未执行，不视为通过。
5. Desktop 的插件链接指向主仓库，正式构建前须确认无活动 Worker 任务。
6. 名称覆盖层不是 DSH 意义上的真改名：DSH 目录里仍是原名，未打补丁的界面（团队看板、工作区树等）和其他读取目录的程序仍显示原名；新名没有在 DSH 中登记，只能靠 tools/pre-execute 拦截与插件自查避免撞名，DSH 其他创建入口可能绕过（未核实）。DSH 原生子 Agent 的身份提示与发出消息的发送者名仍是原名，过渡期对原生子 Agent 只改显示名并在界面标注。工具钩子依赖 list_agents 输出格式与三个工具名，每次升级 DSH 都要回归。只有 DSH 官方提供改名接口才能根除。需真实验证：tools/execute 钩子自行完成 send_message 时工具结果、审计与展示正常；post-execute 替换后模型看到的文本与界面工具卡一致；插件全局钩子能收到主 Agent 与各子 Agent 作用域内的调用；页头列表、面包屑、侧栏标题与冷启动后都显示新名。
7. 插件传入的名称在 DSH 中与同父会话的其他子 Agent（包括主 Agent 用 DSH 自带工具建的子 Agent）冲突时，DSH 会拒绝建立子会话，插件须先避让。
8. OMP 版本更新较快（18.20.0 → 18.22.0），models.yml 的凭据字段与 agent.db 的优先级需按当前版本核实；核实不了时保持原生终端。
9. 「harness」一词过去指外部 Harness CLI（已退役，历史记录仍可查看）；改为指向 DSH 原生子 Agent 后，旧历史记录的显示与续聊须保持只读，不误派。主 Agent 是否按提示调用 subagent 工具取决于模型，需真实派遣验证。

## 八、上线与验证计划

1. 在 cliworker-now-test/test/worktrees 下建独立 worktree 与 OpenSpec 变更实施。
2. 自动检查：类型检查、lint、全量 vitest、上游四包 Vitest、隔离预览包。
3. 真实验收：Mac Desktop rc.5 中派遣多个 CLI Worker 与 DSH 原生子 Agent，核对两处名称，并对空闲与运行中的 Worker 各改名一次，核对子会话 ID 不变、页头列表、list_agents、新旧名称寻址与重启后显示；在主对话发送「调用 dsh …」「用 DeepSeek Harness …」各一次，核对派遣到原生子 Agent 且面板分组标题为 Deepseek Harness；OMP 用虚构测试服务商实写，写前备份、验后恢复，不调用模型；隔离 DSH_HOME 端到端（rc.5 自带 dsh），Mac Desktop rc.5 实机加载与一次真实派遣加续聊。
4. 验收通过后合并到 main、移除 worktree；随 v0.9.2 发布。
