# Proposal

## Why

需求 REQ-0136（快照 `doc/prd/2026-11-17-v0.9.1-REQ-0136.md`）排查登录问题时发现了一份重复安装。

- Windows 测试机的 Pi 原本是官方托管安装：`~\.pi\agent`，1.1.0，排在 PATH 最前。
- 2026-11-15，插件「更新 CLI」页对 Pi 的一次操作在 npm 全局（`%APPDATA%\npm`）另装了 1.5.2，并把插件记录的 Pi 路径改到了新装的那份（revision 2）。
- 结果是插件用 1.5.2，原托管安装停在 1.1.0，终端里直接运行 `pi` 得到的仍是旧版。
- 用户 2026-11-17 要求：更新已有的 CLI 要在原有安装上更新，不能另装第二份；不论用什么方式更新，都应该在原有基础上进行。

代码审查与两台机器的盘点结论：

- 普通的「更新」走原安装的渠道，标准布局下不会换位置。出问题的有三处：
  - 「重新安装」入口不看原安装：它重新选择默认方式（npm 用当前全局前缀，官方脚本用默认目录），装完改写插件记录的路径，旧的一份保留不动。Pi 识别失败（CLI_IDENTITY_MISMATCH）时还会特意放行到这条路。
  - Windows 上 npm 前缀以 `lib` 结尾时被误剥一层；自定义前缀的 `.cmd` 被规范成内部 JS 后，识别不出是 npm 安装。
  - 更新后的核对在写入路径记录之后才做；Windows 桌面安装向导也不核对新版装到了哪里。
- 盘点结果：Mac 上 17 个 CLI 中，插件记录的路径都是 PATH 上排第一的那份；Windows 上由插件产生、且与 PATH 不一致的只有 Pi 一例。
- 另外，两台机器上插件用的 ZCode 都是插件私有运行时 0.16.9，不随桌面应用更新，等于插件另外维护的一份。

## What Changes

- 已有安装分三种状态处理：
  - 不存在：只有这种情况才按默认方式全新安装。
  - 存在但识别不出：报错，说明原安装的位置和应该用的渠道，不安装、不改记录。
  - 已识别：更新、重新安装和修复的结果都必须落在原安装的根目录、前缀或应用目录里。
- 约束只看落点，不限制方式：官方自我更新、npm 下载、镜像、插件接管都可以用，但不能另装成一份。
  - 例：托管安装的 Pi 可以用 npm 上经过校验的安装包作来源，修复或更新到 `~/.pi/agent`；不能装成另一份 npm 全局包。
- 修正 Windows npm 前缀推导；自定义前缀的 `.cmd` 与内部 JS 按包目录统一识别为 npm；Windows 路径比较不区分大小写；初次识别就读取 Pi 托管元数据。
- 官方安装脚本绑定到已核实的安装目录。脚本没法指定目录、目录又不是默认目录时：有同目录接管就走接管，没有就拒绝。
- 更新完成后，先核对仍是同一份安装、版本也对，再写插件的路径记录；核对出是另一份时，记录与 revision 不变，本次报失败。
- Windows 桌面安装向导（ZCode、WorkBuddy、WorkBuddy CN）结束后核对新版的位置；与原位置不同就报失败，不改记录。
- ZCode：不再让插件私有运行时停在旧版，具体方案见设计决定 4。
- 不改变的部分：
  - 官方优先、插件接管只写进 CLI 自己的官方目录、7 天失败记忆（v0.9.0 双通道决定）；
  - Grok、Pi、Hermes 的接管；
  - Bun、pnpm、Nix、Scoop、WinGet 仍需手动更新。

## Capabilities

### Modified Capabilities

- `cli-update`：新增「已有安装只在原安装上更新或修复」「路径记录在安装身份复核后提交」。原有的「平台组件损坏 → 重新安装入口」改为在原安装上修复。

## Impact

- `src/host/cli-management/`（install、新增 repair、identity、planner、service、desktop-update、artifacts）、`src/host/adapters.ts` 及相关测试；README 与 `doc/design.md`。
- 已经存在的重复副本（如 Windows Pi 托管 1.1.0 与 npm 1.5.2）不由本变更自动清理，删除哪一份须用户确认。
- 不涉及登录、凭据与模型调用。
