# Proposal

## Why

连续发送时，本地提交和 Host 准备尚未同步，界面仍可能把第二条消息作为空闲续聊；正文气泡又受到例行尾部提示撑宽。原生协议迁移后需重新核对运行中追加输入能力，按用户确认的 V1 统一提交、停止、队列与插队语义。

## What Changes

- 点击时同步固定消息身份、发送模式和会话占用，准备与清理均算忙碌，回执只对账不重分类。
- 普通队列获得原生启动准入后一次性转消息；旧暂停队列保留暂停，新一轮追加的正常队列独立继续。
- 显式停止以操作边界取消尚未执行提交，迟到回执不得取消此后的新消息；连续插队仅最新未启动请求能执行，已尝试启动的必须停止清理。
- 移除例行发送/取消提示及占位，气泡按正文独立布局，保持用户空白与原生功能条、单按钮和退场动效。
- 对全部 11 CLI 核验并接通已证明的当前运行原生引导；严格区分拒绝、确认和未知，不停止/重启或静默改模式。
- 按用户明确选择，将现有项目发送方式一次性更新为支持引导则引导、其余排队；之后的手动设置仍持久保存。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `worker-conversation-interaction`: 同步提交占用、队列代际与原子准入、停止/插队竞争、正文布局和已核实原生引导默认。

## Impact

影响 Client 提交状态、面板、时间线与动效，Host 运行器/持久队列、Gateway 受理接口、项目发送设置和原生控制邮箱/runner。复用现有受管进程与权限；不修改 Harness 核心，不升级全局 CLI、版本或公开发布。旧 Worker 按实际 transport 判定能力；未核实的原生引导保持不可用。真实模型只使用已授权保存选型，缺少账号/选型与 Windows 实机未验证项单列。
