# Design

## Context

- 更新的执行路径在 `src/host/cli-management/`：identity 识别安装来源，planner 生成计划，service 执行与核对，install 负责首次安装与重新安装，desktop-update 处理桌面应用，artifacts 负责插件接管。
- 插件记录的可执行文件路径存放在 `~/.dsh/cliworker-now/cli-executable-paths/`。`setManual()` 写手动记录并增加 revision，`remember()` 写自动记录；解析时手动记录优先（`src/host/adapters.ts`）。
- 审查结论：普通更新在标准布局下不换位置。出问题的地方：「重新安装」不看原安装且会改写路径记录；Windows npm 前缀与路径大小写；更新后的核对晚于写入记录；Windows 安装向导不核对新版位置。

## Goals / Non-Goals

- Goals：已有安装的更新、重新安装与修复只在原安装上进行；做不到时明确报错，不另装。
- Non-Goals：
  - 不自动删除已经存在的重复副本；
  - 不改变 v0.9.0 的双通道决定（官方优先，接管只写进 CLI 自己的官方目录，7 天失败记忆）；
  - 不支持 Volta、pipx、uv 等尚未识别的包管理器。

## Decisions

### 决定 1：已有安装分三种状态，结果必须落在原安装

用户 2026-11-17：「更新已有的cli是在原有的基础上进行更新，而不是装第二个」；补充：「pi的更新逻辑不应该是禁止npm，而是不论用什么方式更新都应该在原有基础上进行更新」。

| 状态 | 判定 | 处理 |
| --- | --- | --- |
| 不存在 | PATH、插件记录与已知目录都没有 | 按默认方式全新安装 |
| 存在但识别不出 | 有安装文件或元数据，但来源无法核实 | 报错，说明位置与应用的渠道；不安装、不改记录 |
| 已识别 | 来源、根目录与前缀已核实 | 任何渠道都可以，结果写回原 root、prefix 或 appPath |

- 约束只看落点，不看渠道：官方自我更新、npm 安装包、镜像、插件接管都可以用。
- 例：托管安装的 Pi 可以把 npm 上经过校验的 tarball 作为来源，经环回 registry 交给官方 `pi update --self`，写入 `~/.pi/agent`；不能装成另一份 npm 全局包。
- 核对三件事：原安装已经是目标版本；没有在其他根目录或前缀里出现新的一份；插件记录仍指向原安装。
- 现行规格「已安装版本等于最新但平台组件已损坏 → 提供已有重新安装入口」随之收窄：入口保留，含义改为在原安装上修复。
- v0.9.0 页面设计允许 Pi 不可用（unusableBefore）时改走 npm 另装，此条作废。
- 放弃的方案：先按默认方式安装再切换路径，因为会造成重复安装。

### 决定 2：只读发现，核对后才写路径记录

- 管理页的安装发现使用不写路径存储的模式，不调用 remember 或 reset。
- 核对仍是同一份安装之后，才提交记录。核对出另一份安装时报失败，记录与 revision 都不变。
- 放弃的方案：失败后回滚记录。原因是写入时 revision 已经变了，并发修改也可能已经发生。

### 决定 3：官方脚本与安装程序以证据为准

- 官方安装脚本有目录参数或环境变量时，传入已核实的根目录；参数以官方脚本源码为证据，不猜测。
- 脚本只能装到默认根目录、而现有安装不在默认根目录时：有同目录接管就走接管，没有就拒绝。
- Windows 桌面应用继续使用可见的安装向导（「Windows 官方安装程序窗口可见且等待用户时不限时」仍然有效）。安装程序整个进程范围退出后，核对注册表和应用查找到的实际位置，与原位置相同才写记录。
- 放弃的方案：猜一个统一的 `--dir` 参数，或改成静默安装。没有官方证据，也违反窗口可见的规则。

### 决定 4：ZCode 不再让插件私有运行时停在旧版

- 现状：
  - 插件用的是 2026-10-05 从官方源码自建的私有运行时（CLI 0.16.9）。当时桌面应用自带的 CLI 缺少 `login [zai|bigmodel]` 等能力。
  - 更新页显示的 3.18.2 是桌面应用的版本，Worker 实际运行的是 0.16.9；插件没有任何刷新这个运行时的逻辑。
- 用户 2026-11-17 选择改用桌面应用自带的 CLI。只读核实结果（未调用模型）：
  - 自带的 0.17.1 与插件的协议兼容，`--help`、Worker 参数、app-server 握手、无轮次会话和能力探针都通过。
  - 但它缺少 `@zcode/tui`（管理终端会报错）、`playwright-core`（浏览器操作）和 `@napi-rs/keyring`。Windows 自带的文件与 Mac 逐字节相同，也缺这几个依赖。
  - 因此不能直接切换。
- Fable 的分析与用户 2026-11-17 的决定：按桌面应用自己的方式运行它自带的 CLI。
  - 启动方式：
    - 可执行文件：ZCode 应用自己的 Electron（Mac `<app>/Contents/MacOS/ZCode`，Windows `<root>\ZCode.exe`）；
    - 环境变量：`ELECTRON_RUN_AS_NODE=1`；
    - 参数：`--require <插件解析钩子> <resources>/glm/zcode.cjs …`，后面原有的参数不变。
  - 解析钩子只在正常解析失败时，把 `@napi-rs/keyring` 与 `playwright-core` 指向同一个应用的 `app.asar`，所以依赖版本天然与 CLI 一致。
  - 管理终端（tui）的依赖没有随桌面应用发布，入口隐藏；登录与退出按钮不受影响。
  - 凭据：插件 ZCode 账号目录尚未固定使用系统凭据库时，生成 0600 的 `credential-secret`（这是 ZCode 原生支持的方式），避免 macOS 钥匙串授权弹窗。旧的 `enc:v1` 值由 ZCode 自己在下次使用时改写为 `enc:v2:env`，此后旧的 0.16.9 无法读取。
  - 用 ZCode 自己的 Electron 探测 `--version` 失败时（例如以后关闭了 RunAsNode 开关），回退到 Host 运行时并提示。
  - 放弃的方案：
    - 在原目录重建私有运行时：仍然是插件另外维护的一份。
    - 由插件补齐依赖：版本匹配脆弱。
    - 官方独立发行版：没有发布。
- 无论采用哪个方案：迁移只针对自动路径记录，手动路径与显式配置不动；更新页同时显示「应用 X · CLI Y」；旧的私有运行时只在迁移成功、没有进程在用、并经用户确认后才删除。

## Risks / Trade-offs

- 识别不出来源的安装，从「另装一份」变成「报错」，用户需要用原渠道修复。这是用户要求的取舍。
- 已有的重复副本不会消失，清理须用户逐项确认。
